两条，直接能用：

1. **先让它复述再动手**：把任务拆成「只改哪个文件、哪个函数、改完应该是什么样」，让它先说一遍计划和要动的范围，你确认后再让它改。一次只改一处，改完你跑一遍，过了再下一个。

第二条其实是约束它的手，第一条是约束它的脑子——两个一起用，它想乱改也没地方乱改。

## 初版 T07 · 2026-11-10.1

用户：Python 里怎么把列表按数字从小到大排序？给个例子就行。

成功：True；耗时：1.50 秒；结束：stop；截断：False。

用 `sorted()` 排完会返回一个新列表，原来的列表不变；直接改原列表就用 `list.sort()`。

```python
nums = [5, 2, 9, 1, 7]

ascending = sorted(nums)
print(ascending)   # [1, 2, 5, 7, 9]
print(nums)        # [5, 2, 9, 1, 7]，原列表没动

nums.sort()
print(nums)        # [1, 2, 5, 7, 9]，原列表被改成了升序
```

如果列表里混有不能直接比较的东西，例如字符串和数字，这两种写法都会报 `TypeError`。

## 最终版 T04 · 2026-11-10.2

用户：AI 又把代码改乱了，真烦。给我两条具体办法，减少这种乱改。

成功：True；耗时：3.71 秒；结束：stop；截断：False。

改得乱，多半是它一次动的地方太多、动完你也没法一眼验收。两条最管用的：

**一、先要方案，再让它动手。** 开口就把范围钉住：「先只列出要改哪几个文件、每个文件改什么、为什么，给我 diff，不要直接写入。」看完 diff 再说「按这个改」。它想顺手「优化」别的文件时，你有个拦下来的机会，而不是事后从一堆改动里找哪句是它自己加的。

**二、一次只改一个点，改完立刻留痕。** 每次提需求前先 `git commit` 或 `git stash`，把当前能跑的版本存住；然后一次只让它做一件事，比如「只修这个函数里的空值判断，其他别碰」。改完先看 `git diff` 验收，能跑再提交。

真被改乱了，`git diff` 看清它碰了哪些地方，`git checkout -- 文件名` 把没提交的恢复回来，你原本的工作不会跟着丢。
