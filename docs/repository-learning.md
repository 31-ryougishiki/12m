# 知识图谱源码学习原型

目标是帮助用户从仓库结构、请求流程、设计取舍逐步走到代码细节，并通过复述与验证发现知识缺口。第一版先建立“定位源码 → 理解当前步骤 → 自测 → 继续探索”的闭环。阅读次数和生成解释不代表掌握程度。

## 已有实践与采用方式

| 实践 | 可借鉴的能力 | 本项目的处理 |
| --- | --- | --- |
| [CodeTour](https://github.com/microsoft/codetour) | 将讲解绑定到文件、行及版本，逐步导览 | 使用学习顺序边连接节点；与调用关系分开 |
| [VS Code 调用层级](https://code.visualstudio.com/docs/cpp/cpp-ide) | 查看调用者和被调用者 | 后续接入符号索引，第一版只提供已有关系，不能当作真实调用栈 |
| [GitHub 永久行链接](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-a-permanent-link-to-a-code-snippet) | 定位特定版本的代码行 | 使用完整 commit SHA，拒绝 main 等漂移定位 |
| [Retrieval Practice](https://www.retrievalpractice.org/faq) | 通过回忆和反馈促进学习 | 先写复述，再请求反馈；不根据模型评价自动授予“专家”状态 |

源码学习最有价值的上下文不是更多百科知识，而是解释当前决策所需的最少证据。以下设计是本项目的产品选择，不是上述资料给出的统一标准。

## 当前实现

图谱页点击“体验 vLLM / Ascend 源码导览”会创建一个用户专题，空存档不自动注入示例。四个节点均附带实际读取的源码片段和固定提交链接：

1. vLLM Scheduler.schedule：观察调度过程的 token 预算。
2. KVCacheManager：观察缓存块管理职责。
3. Ascend NPUPlatform：观察平台接口边界。
4. AscendAttentionBackend：观察后端与实现类的分工。

这四步是学习顺序，不是运行时调用链。vLLM 快照为 `c6573eed5e56fd39b01d610db04616ed9b221851`，Ascend 快照为 `fa4ce1bcd3ecc449265f380e117b3b17ebdac00c`，采集日期为 2026-11-12。两个仓库独立取样，不声明是兼容版本组合。

节点详情保持现有浅色像素界面，增加固定源码行入口、学习目标、API 讲解和折叠自测。复述保存在该节点中，可随存档序列化。候选资料默认折叠。学习设置可以填写目标、问题和固定代码链接；扩展资料通过 DSH 的 Learning.Evidence 导入。

API 讲解只读取传入的片段与上下文，不修改图谱，不自动联网抓取链接。输出明确标注待核实。已有普通节点也可以补充学习设置。

## 五类扩展资料的取舍

| 类别 | 应呈现的信息 | 纳入条件 |
| --- | --- | --- |
| 代码与 PR | 输入输出、调用上下文、设计取舍、替代方案 | 代码事实绑定提交；作者动机必须有 PR 原文，blame 本身不证明动机 |
| 特性来源 | 算法论文、社区提出过程、作者博客 | 分开“论文提出算法”和“当前实现采用算法”，不轻率声称最早来源 |
| 设计模式 | 接口、职责、变化点、代价 | 默认解释实际结构；“适配器/策略”等名称属于分析推断，不能只匹配类名 |
| 语言与数学 | 阻碍当前理解的高级语法、张量形状和公式 | 按需展开；公式对应具体变量与维度，避免每节点附一章教材 |
| 外部算子与仓库 | 输入、输出、dtype、shape、设备约束、实现出处 | 先给规格再给实现；跨 torch_npu/CANN 边界时记录各自版本 |

可用的第一手材料包括 [PagedAttention 论文](https://arxiv.org/abs/2309.06180)、[作者团队的介绍博客](https://vllm.ai/blog/2023-06-20-vllm)、[vLLM 插件设计](https://docs.vllm.ai/en/stable/design/plugin_system/) 和 [Ascend 设计文档入口](https://docs.vllm.ai/projects/ascend/en/latest/developer_guide/Design_Documents/index.html)。论文和早期博客适合理解分页缓存的背景；其中的性能数字及历史实现不能直接移植到当前版本。插件文档适合理解平台注册边界，具体实现仍以固定提交为准。

## 筛选机制与验证

第一版使用可解释门槛，暂不使用模型自报的置信度分数。候选资料必须包含 HTTPS 来源、原文依据、与节点的关联说明、完全匹配的适用版本，并经用户核对，才进入默认展示；按导入顺序去重，最多三条。其它资料保留在折叠区并显示排除原因。这里的“原文依据”允许简短摘要，仍需人工与原文比对。

AI / DSH 导入不能认证 Reviewed，且不能代填用户 Reflection。Learning 是整体替换字段，省略则保留；更新已有资料后必须重新核对。此门槛检查证据完整性，不能证明语义支持，也不能发现伪造摘录。源码链接校验验证格式，不自动检测链接是否可访问或代码片段是否吻合。

离线测试覆盖固定链接、危险协议、版本错配、缺失依据、未审核、重复来源、三条上限、序列化、AI 只读输出、导入伪造审核和复述。WPF 渲染覆盖真实四步示例及折叠候选区。测试 API 使用替身，不代表真实模型讲解质量已通过评测。

后续应建立至少 30 个真实节点的人工标注集，混入旧版本文档、相关但不支持结论的论文、伪造 PR 动机、同源转载、跨仓库版本不匹配和无关数学说明。分别统计默认展示准确率、可用信息召回率、证据蕴含判断和单节点阅读负担。目标可暂定默认展示准确率 ≥95%，但这不是当前已达到的指标；采用独立保留集后才能判断成熟度。

## 下一轮开发

本地固定提交读取、片段校验和符号搜索已接入代码问答。后续补齐自动调用关系分析，再接入 PR/issue 搜索。抓取结果需记录时间、内容摘要和支持的具体断言；来源的权威性与断言是否被支持分别判断。候选生成、证据验证和呈现应分阶段，失败时保留“未知”。

学习路径从一条完整请求逐步扩展为架构、调度与缓存、设备适配、算子细节四条支线。增加先修节点、返回路径和跨版本失效提示；通过“解释行为 → 预测修改影响 → 定位真实问题 → 提交小修复”的任务证明能力。间隔复习与知识缺口推荐应以用户实际作答为依据。

目前未实现自动 PR 溯源、自动发现高质量博客、任意仓库索引、真实算子规格抓取、自动专家评定。这些应在证据管线和真实模型评测建立后逐步加入。


## 本地阅读与分段展示

已增加原文要点卡片和按需展开，避免将实现思路一次铺满侧栏。已支持按仓库配置本地目录，在 VS Code / Cursor 打开文件；精确行跳转前比对 Git blob 与工作区文件，无法确认时打开文件开头。此核对仅证明当前文件内容相同，不证明依赖、环境或整个仓库版本兼容。实现方式采用 [VS Code 官方 --goto 参数](https://code.visualstudio.com/docs/configure/command-line)。

测试覆盖中文及空格路径、工作区改动、缺失文件、路径穿越、编辑器参数、配置保存和分段原文保留；WPF 渲染覆盖要点折叠与本地入口。


现有源码专题新增架构投影：先按两个仓库和职责模块建立空间位置，再进入代码节点与普通生成请求旅程。实现与适用范围见 [仓库架构总览](knowledge-graph.md#仓库架构总览原型)。当前实现仍是基于已有节点的精选地图，不声称完整覆盖仓库，也不以点击或阅读次数判断掌握程度。

## 图谱问答通过 DSH 阅读源码

普通聊天中的图谱代码问题、联网后的代码问答和节点讲解共用 `GraphReadingSnapshot.Complete`。曳尔沐先输出普通文本的 `DSH_READ` 阅读要求，宿主调用本机 DSH 桥接，以 `read-only` 权限创建任务；DSH 直接检索本地仓库、读取定义和调用方，返回结论及代码位置。宿主收到完成结果后，再让曳尔沐围绕用户原问题整理回答。此流程不再调用 `SourceResearch.Complete`，也不自动附加宿主读取的源码片段；旧 `SOURCE_READ` 标记若从历史中出现，将按原问题转交 DSH，不解析模型生成的查询 JSON。

任务包含发送问题时捕获的专题焦点、仓库绝对路径、固定 commit、源码入口和最近对话，便于解析“这里”“后续在哪里使用”等指代。DSH 必须核对指定版本，不修改源码或图谱，不执行安装、构建、测试、checkout 或 fetch。只读问答自动提交，不沿用一般 DSH 写入任务的完整访问设置。用户需启用 DSH 插件与委托，并运行配置了本项目桥接插件的 DSH。

每个问题最多创建一个 DSH 阅读任务，宿主等待最多约4分钟（单次网络请求另有超时）。界面显示阅读阶段和工具次数。应用关闭或任务超时会请求取消对应 DSH job。连接失败、任务失败、无工具调用、空结果或不匹配的任务 ID 均明确报错，不转回原本的源码查询流程，也不把尚未完成的进度当作结论。写代码仍走独立委托流程。

查询诊断位于 `%LOCALAPPDATA%/ElymsDesktopPet/dsh-source-research/yyyyMMdd.jsonl`，记录请求 ID、DSH JobId、阶段、状态和工具次数，不记录认证 token。DSH 会话中可以查看实际工具记录。明确选择的文字重写仍可使用已有的固定版本片段核对功能。

## 修改节点前核实源码

图谱中的 AI 修改/新增节点、模块编辑和聊天触发的图谱编辑共用 `RunGraphAi` → `GraphReadingSnapshot.CompleteEdit`。模型先返回 `RequiresSource` 和核实问题：展开代码细节、核实字段用途、纠正实现或调用关系、基于实现新增节点时必须查源码；仅改标题、措辞、等级、模块归属或学习组织关系，以及不涉及代码的普通图谱编辑不必调用 DSH。混合要求按需要查源码处理。此判断由模型进行，缺少映射不能作为跳过查证的理由。

需要源码时，宿主以 `read-only` 权限提交一次“图谱编辑 · 阅读本地源码”任务，携带固定 commit、本地目录、节点焦点和核实问题。DSH 只阅读代码，不写图谱；返回 `Verified`、`Findings`、`Sources` JSON。宿主要求真实工具调用、非空结论、`Verified=true`，并校验来源为当前仓库及提交的固定行链接。检查通过后，曳尔沐才生成 `GraphEditRequest`，将证据附到相关节点或关系，再沿用原有范围、Revision、结构和原子保存校验。固定行链接格式与版本检查不能单独证明语义正确性，结论仍依赖 DSH 的源码核实。

编辑状态栏显示“正在思考”、DSH 阅读工具次数及整理节点修改阶段。DSH 禁用、连接或核实失败、版本来源不符、结果不完整时均保留原图谱并显示原因。等待 DSH 期间发生的图谱修改由既有 Revision 校验保护。纯文字或组织调整无需 DSH 可用，但仍需 AI 连接。手动编辑节点表单不调用 DSH。

回答直接说明代码行为，保留常见英文术语，不强制术语表、例子、自测题或思考式开场。默认简短，用户明确要求详细或问题复杂时展开。

图谱编辑使用独立的结构化输出通道，允许最多 262144 字符，避免完整 JSON 被普通存档的 24000 字符限制截断。修改结果首轮输出预算为 32768 tokens，失败后最多重试一次，预算提高到 65536，并要求只返回必要增量；源码核实分流使用较小预算。重试只重新生成模型结果，复用本轮 DSH 证据，不重复提交源码任务。截断、非法 JSON、版本冲突仍不保存任何修改。`graph-edit-diagnostics/yyyyMMdd.log` 仅记录阶段、结束原因、字符数、token 用量及本机截断标志，不保存提示词、图谱正文、凭证或思考文本。
